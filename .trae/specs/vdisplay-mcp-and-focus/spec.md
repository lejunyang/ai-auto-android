# 虚拟显示的 MCP 出口与焦点隔离规格

## 目标

1. 让 MCP 客户端（AI Agent）能在虚拟显示上观察和操作，而不是只能通过 CLI。
2. 消除「不带目标显示的层级读取在虚拟屏持有焦点时读到虚拟屏内容」的歧义，给出
   一条明确指向主屏的读法。
3. 用实测回答：在虚拟屏上自动化时，用户在主屏的输入焦点与输入法是否被打断；
   能缓解则缓解，不能则如实记录为限制。

本规格建立在 `.trae/specs/virtual-display-screen-off/` 之上，沿用其全部安全边界。

## 决策记录（用户 2026-11-14 确认先做 MCP 出口与焦点）

1. **辅助进程的启动与停止仍然只有 CLI 出口**。它会向设备部署并运行一个 shell 身份
   进程，属于操作员级准备动作，与 Bridge 配对同级；MCP 不提供 `display start/stop`。
2. **MCP 新增虚拟屏管理走独立风险门**，与文件传输的独立门并列，不并入既有的
   模型动作白名单：列出与状态是只读；创建有数量上限；关闭会销毁其上应用内容，
   必须在工具描述里写明。
3. **目标显示不扩大动作面**。只有 MCP 上已经允许的动作才能带目标显示；带目标显示
   不会让任何原本被拒绝的动作变成允许。
4. **显示编号 0 表示「明确指向主屏」**，在 CLI 与 MCP 上都接受，不要求辅助进程在
   运行。不带目标显示的既有行为与命令行保持逐字不变。
5. **不绕过锁屏**、不捕获安全窗口、失败不回退主屏——沿用上一规格。

## 设计

### 明确指向主屏（显示编号 0）

- 层级：发出 `uiautomator dump --windows`，只返回 `display id="0"` 的窗口组，形态为
  `uiautomator-windows-xml`。API 门槛沿用上一规格（AOSP Android 11 起解析）。
- 截图：与现有主屏截图同一路径。
- 点按、滑动、按键、文本、启动：分别带 `-d 0` / `--display 0`。
- 显示编号 0 不经过辅助进程的归属校验；正整数编号仍必须属于辅助进程。

### MCP 出口

- `android_observe`：`screenshot` 与 `hierarchy` 接受可选 `displayId`（非负整数）。
  结果里带上实际读取的显示编号与层级形态。其它观察类型拒绝该参数。
- `android_action_execute`：已允许的坐标与按键类动作、应用启动接受可选 `displayId`。
  具体哪些动作可带，由实现时对照既有风险门逐项核对并在规格进度里列表说明。
- 新增虚拟屏管理工具（名称由实现时对照既有命名确定）：列出与状态、创建、关闭。
  输入 schema 用 `additionalProperties:false`；不暴露标志位、套接字、helper 路径。
- `device.sleep`：仅当 `device.wake` 已在 MCP 上允许时，才以对称方式开放；否则
  保持不开放，并记录理由。
- 视觉候选与视觉动作工具、`android_wait` / `android_assert` / `android_scroll_until`、
  Bridge 相关工具**本规格不接入目标显示**，传入该参数时明确拒绝。登记为后续项。
- 辅助进程未运行时，带正整数显示编号的调用返回 `DISPLAYD_NOT_RUNNING`，并在消息里
  指出需要操作员先执行 `aactl display start`。

### 焦点与输入法实测

在 API 35 模拟器上构造「用户正在主屏输入」的状态，然后在虚拟屏上执行自动化，逐项
记录主屏是否受影响：

1. 主屏：一个输入框获得焦点、输入法弹出、已输入部分文本。**使用系统设置的搜索框**
   （见下方 2026-11-14 修订），不用 fixture。
2. 虚拟屏：fixture 应用（其输入框在 720×1280/240dpi 下有可点按的露出部分）。依次执行点按非输入区域、点按输入框、
   `action text`、按键、启动另一个应用。
3. 每一步之后记录：主屏的焦点窗口与焦点应用、输入法当前服务的客户端及其所在
   显示、输入法是否仍显示、主屏输入框内容是否变化；再向主屏输入一个字符，确认
   它落在主屏输入框。
4. 证据取自不受焦点歧义影响的来源（按显示分段的 `dumpsys`、显示编号 0 的层级）。

若发现打断：尝试只用固定框架调用的缓解手段（例如给虚拟屏设置输入法策略，使其
不抢占输入法），并重新测量。缓解有效则实现并写入契约；无效或只部分有效，则把
实测结果原样写进文档的限制说明。**不得为了「通过」而弱化测量或改写判据**。

### 修订（2026-11-14，集成方实测后）

- **基线应用更换的原因**：fixture 的输入框在 API 35 的 edge-to-edge 布局下被标题栏
  盖住。主屏 320×640/160dpi 时其 bounds 为 `[12,31][308,79]`，完全落在状态栏与
  标题栏（至 y=80）之下，点按永远落在标题栏上，所以无法聚焦。这是 fixture 的布局
  问题，与焦点隔离无关；本规格不修改 fixture，登记为后续项。
- **缓解手段已由集成方在模拟器上验证有效**：创建虚拟屏时在 API 34+ 追加
  `VIRTUAL_DISPLAY_FLAG_STEAL_TOP_FOCUS_DISABLED`（`1 << 16`，标志位合计 `130507`）。
  本规格据此允许修改 `android/displayd/` 的固定标志位及其测试与文档；标志仍由代码
  固定，不由调用方传入。API 33 没有该标志，保持原样并如实记录为未缓解。
- 逐步数据见 `progress.md` 的「集成方焦点实测」。实现后仍须由脚本独立复现未缓解
  与缓解后两组结果，不能直接引用集成方的手工数据作为验收证据。

### 修订二（2026-11-14，集成方实测后）：焦点策略二选一

实测发现「不抢占顶层焦点」与「主屏息屏时读取虚拟屏层级」互斥（数据见 `progress.md`
的「集成方定位：息屏后窗口列表为空」）：

- 带 `1 << 16` 的虚拟屏：不打断主屏输入；但主屏息屏后 `uiautomator dump --windows`
  不产生任何输出，虚拟屏层级读不到。主屏唤醒后恢复。取帧与输入注入不受影响。
- 不带该标志的虚拟屏：主屏息屏后仍能读到虚拟屏的窗口分组；但会抢占顶层焦点并
  打断主屏输入法。

两种用法正好对应两类场景，因此创建虚拟屏时增加一个**二值的焦点策略**，由代码把
它映射到固定的标志组合，仍然不接受调用方传入原始标志位：

| 策略 | 标志 | 适用场景 | 已知代价 |
| --- | --- | --- | --- |
| `isolated`（默认） | API 34+ 含 `1 << 16` | 有人在用主屏，不能打断输入 | 主屏息屏时读不到层级；虚拟屏无输入法 |
| `steal` | 不含 `1 << 16` | 无人值守、主屏息屏挂机 | 会抢占顶层焦点并打断主屏输入法 |

- CLI：`aactl display create ... --focus isolated|steal`；MCP 的创建工具增加同名
  枚举字段。`display list` / `status` 返回每块屏的策略。
- API 33 没有该标志，两种策略的标志相同；`isolated` 在 API 33 上必须如实报告
  「无法隔离」，不得静默当作已隔离。
- `isolated` 的屏在主屏息屏时读层级，返回可区分的错误并说明原因与出路（唤醒主屏，
  或改用 `steal` 策略重建），不得报成「XML 无效」。
- 默认取 `isolated`：在有人使用的设备上，默认行为不应打断用户。无人值守场景需要
  显式选择 `steal`。

## 不做的

- MCP 上的辅助进程启停、视觉工具与等待/断言/滚动直到的目标显示。
- 虚拟屏上的中文输入。
- 真机、API 33/34 的结论。
- 发布打包、摄像头、文件传输。
- 修改 `docs/next-phase-tasks.md` 与本规格未列出的 `docs/` 文件（另有并行的文档
  清理任务拥有这些文件）。

## 验收

- Go：显示编号 0 的各条命令行有 fake-adb 测试；不带目标显示时逐字不变的测试继续
  通过；MCP 的 schema、风险门、错误映射有测试，包含「带目标显示不放宽动作面」与
  「未接入的工具拒绝该参数」。
- 模拟器端到端（API 35，`-read-only`，显式 serial，记录指纹）：通过真实的 MCP
  stdio 会话完成「列出虚拟屏 → 在虚拟屏启动 fixture → 读层级 → 点按 → 读层级确认
  变化 → 截图 → 读显示编号 0 的层级确认仍是主屏内容」。连续 3 次。
- 焦点实测的逐步结果表写入规格进度与 `docs/virtual-display.md`。
- `make comments`、`make test`、`make verify`、`make build`；改到 `android/` 时
  `make android-verify`。
- 无设备证据的项保持未勾选。

## M3c实施决定（2026-11-14）

- 焦点策略字段统一命名focus（CLI为--focus），取值isolated/steal，省略默认isolated。
  helper协议提升为v2，传输端点仍aactl-displayd-v1；客户端拒绝版本不匹配，不猜测旧helper策略。
- create/list/status每块屏返回focus与focusIsolated。后者表示当前API下启用了隔离标志，
  不是OEM实测保证；API33始终false，hello.capabilities.focusIsolation为API34+。
- 原始标志仍拒绝；API33两策略15819，API34+ isolated=130507、steal=64971，均排除SECURE。
- 无文件/空窗口输出用WINDOWS_UNAVAILABLE提示唤醒主屏或steal重建；有效XML中的空屏仍
  DISPLAY_EMPTY，未归属仍DISPLAY_NOT_FOUND，畸形/截断XML仍拒绝。CLI通用退出码10不变。
- 原验收脚本明确使用steal，另扩展焦点测量脚本为isolated完整场景。两场景各须三个
  完整冷启动通过后再进入M4/M5；目前steal已三次通过，isolated首轮主屏基线失败，阶段未验收。

## 脚手架停机规则修订（2026-11-14，用户授权恢复）

基线/等待/选择器/环境抖动/脚本解析与清理失败属于脚手架问题，应保留当时原始证据，
自行修复并补脚本测试，然后从冷启动重新计数。只允许重新观察后行动与有上限条件等待；
不能盲目重复、延长固定睡眠或降低被测判据。同一脚手架问题连续修复3次仍不稳定则停止，
附上各次原始证据。产品行为矛盾、无法解释的产品结果、越过文件或安全边界仍立即停止。
失败证据须在重试/清理前保留实际触发判据的脱敏完整层级、截图、dumpsys分段及时间线，
不得以事后重新读取的层级替换原始观察。

当前产品验收阻塞：Round19原始dump未产生文件，而CLI返回ACTION_FAILED/无效XML，
尚未满足WINDOWS_UNAVAILABLE契约。按产品问题停机，不降低错误判据、不越过M3c进入M4/M5。
