# 过期文档审计规格

## 目标与基线

在 `docs-stale-audit` 分支、`E:/Projects/wt-docs-audit` 独立 worktree 上，以开工基线
`984ee31` 核实文档中的现状断言，修正活文档，给历史记录补现状更正，避免把历史缺口
继续当成当前能力边界。审计日期为 2026-11-14，不以本轮文档核查代替设备验收。

## 方法与判定规则

1. 阅读 `AGENTS.md`、根 README、`docs/` 全部 Markdown，以及既有规格的
   `spec.md` / `tasks.md`，逐份记录可核查的能力、数量、缺口和验收状态断言。
2. 对照当前实现、测试定义与 git 历史；证据使用文件行号、测试名或提交 hash。
   只有证据成立才更正，无法核实则注明原因，保留未验收状态。
3. 导航、路线图、架构、能力清单等活文档直接更正并保留后续规格指向；带日期的
   评审、验证、verdict 和基线评估只在文首添加带日期的现状更正，原正文不改。
4. 路线图逐任务检查勾选状态：实现不能替代实测，阶段性交付不能替代整项验收。
   不回写 MVP 或任何既有规格，不篡改历史结论。
5. `progress.md` append-only，保存逐文档断言清单、每条改动的证据、保留项、
   未核实项和越权文件移交项；核对 Markdown 相对路径与锚点。

## 文件所有权

- 可写：`docs/` 下除 `virtual-display.md`、`protocol.md`、`architecture.md` 外的
  全部 `.md`，以及 `.trae/specs/docs-stale-audit/`。
- 只读：根 `README.md`、上述三份文档、`skills/`、所有既有规格及代码/测试/配置。
  发现问题只记录文件、位置、原断言、证据和建议改法，由集成方处理。
- 不处理 `.html`；不改代码、测试、脚本、配置、Makefile、CI；不下载、不新增依赖、
  不 push、不动其他 worktree 或分支，不启动模拟器或操作任何设备。

## 步骤、依赖与提交边界

- D1：建立本规格并单独提交 `docs(spec): add stale documentation audit change spec`。
- D2（依赖 D1）：只读核查与逐文档清单，确定历史/活文档分类和证据。
- D3（依赖 D2）：修正路线图与能力状态；独立 `docs:` 提交，附同批证据。
- D4（依赖 D2）：历史文首更正、补导航与链接；按主题少量 `docs:` 提交。
- D5（依赖 D3/D4）：验收、范围检查、记录验证结果与未核实项并提交收尾记录。

本轮由单一审计任务串行维护所有共享文档与规格状态，不派发 Sub-Agent；与外部并行
任务的汇合点是 `progress.md` 的只读文件移交清单。

## 验收与回滚

- 所有 `docs/*.md` 有分类与断言核查记录；路线图每个任务有状态核查结论。
- 每条修改断言都有明确证据，历史正文未改写，禁止写入的文件 diff 为空。
- 导航覆盖全部现有 Markdown；相互引用和相对链接经只读检查。
- 执行 `make comments`、`make verify`、`git diff --check`；纯文档任务不运行设备任务。
- 汇报提交 hash、文档计数、重要发现、移交项、未核实项和最终工作区状态。
- 若核查失败，保留未核实说明；若修改不成立，仅撤回本任务拥有文件中对应改动。
  回滚已提交内容用单一职责 revert，不用 reset/checkout/clean 覆盖未知改动。
